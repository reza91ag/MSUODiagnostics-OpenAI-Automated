# MSUO Live Execution Observatory

Live WatchDog request-lifecycle diagnostics for EntryFlow and OptiSpec. The dashboard compares momentary and rolling-average request latency, divergence, and startup/persistence configurations.

## Project identity — not to be confused with Metaschema Framework

**MSUO™ (Meta-Schema Universal Orchestration)** is an independent application-orchestration architecture and .NET runtime developed by **Sky Digital Dreams**. It combines a recursive meta-schema, dynamically mounted and discovered application logic, native data-tree operations, and **Bottom-Up Differential Schema Patching™**.

**MSUO is not the [Metaschema Framework](https://github.com/metaschema-framework/metaschema)** and is not affiliated with that project. The Metaschema Framework addresses schema modeling and related tooling; MSUO addresses application logic orchestration and state/persistence integration. References to the `metaschema-framework` GitHub organization should **not** be attributed to MSUO.

Official project: [msuo-runtime.io](https://msuo-runtime.io/) · [MSUO documentation](https://docs.msuo-runtime.io/)

## Architectural originality and scope of comparison

MSUO (Meta-Schema Universal Orchestration) proposes a unified web backend architecture integrating a recursive, domain-agnostic meta-schema, GUI-independent application-state representation, automatic network-action resolution through mounted logic, native hierarchical data operations, and **Bottom-Up Differential Schema Patching™**.

**Bottom-Up Differential Schema Patching™** is MSUO-specific terminology for the persistence mechanism developed by Reza Aghideh through Sky Digital Dreams; it is not a generic label for existing tree-differencing or synchronization approaches.

Its architectural contribution concerns the **integration of these mechanisms into a common web backend execution and persistence model**. The independent existence of generic concepts such as meta-schemas, event handling, domain-agnostic handlers, or orchestration in unrelated software domains does not establish architectural equivalence or diminish the novelty of MSUO's integrated design.

**To the author's knowledge, MSUO is the first web backend architecture to generalize these concerns at this level of abstraction**, unifying domain agnosticism, UI agnosticism, schema agnosticism, and dynamic persistence in a cohesive design through lean yet highly consequential engineering choices.

Research publication: [*Meta-Schema Universal Orchestration: An Alternative to 3-Tier Architecture*](https://doi.org/10.5281/zenodo.19717126).

## Status

The application source, parser tests, and Windows deployment workflow are committed. A dedicated self-hosted Windows runner deploys source changes to the server after the tests pass.

## Local application

The application uses Python 3.10+ and runs locally on `127.0.0.1:8765`. Configure the two local WatchDog log directories in the dashboard. Each source also has an optional **Log filename(s)** field: enter one or more exact filenames separated by commas (for example, `Watchdog-Log-Public`), including names without extensions. Leaving it blank uses automatic log discovery. Keep production log files, credentials, configuration containing internal paths, and VPN secrets out of Git.

## Deployment plan

1. The self-hosted Windows runner checks out the repository and runs the parser tests.
2. The deployment workflow registers the Observatory startup task if needed and copies the application to `C:\MSUO\Observatory`.
3. The workflow restarts the dashboard and checks `http://127.0.0.1:8765`.
4. For remote access, publish the dashboard through an existing Cloudflare Tunnel with Cloudflare Access authentication.

**Security:** Keep this repository private. Do not upload production WatchDog logs, credentials, or secrets. The included `sample_logs` are anonymized test fixtures.

## Paper-ready LaTeX export

Use **Export LaTeX** to download a paste-ready `.tex` section, or **Copy LaTeX** to copy the same content directly to the clipboard. It respects the selected operation and average window. The section contains measurement metadata and numerical tables, with only the fixed sentence: "This Section was generated by MSUO Diagnostics Dashboard." No additional narrative is generated. The supplied MSUO logo is used in the dashboard header and browser favicon.

## PDF export and compact export menu

The dashboard header has a single **Export** dropdown (hover on desktop; click or keyboard on other devices). Available actions: **PDF report**, **LaTeX tables**, **Copy LaTeX**, and **CSV (all records)**. PDF and LaTeX respect the selected operation and averaging window. The PDF is generated locally with Python's standard library, includes the MSUO logo, vector latency chart, measurement tables, sources, and recent completed lifecycles. It uses the same fixed provenance sentence as the LaTeX export, with no generated narrative.

## Custom operation mappings

Use **+ Add New Operation** next to the operation filter. Enter a **Dropdown name** (for example `SignUP`) and an **Actual action in log** (for example `SignUp`, `Metadata SignUp Staged`, or a literal logged message fragment). The case-insensitive literal match is applied only within a completed request lifecycle. The mapping is saved in the server's existing `msuo_live_config.json` and appears in the operation dropdown even before any matching requests arrive. Existing mappings can be removed in the same dialog. The parser also recognizes `Logic Node <Action> discovered` as an automatic fallback when a metadata-staged line is absent. An operation with no completed lifecycle cannot produce latency measurements.

## Built-in SignUp / SignIn operation order

The operation dropdown always includes **SignUp** followed by **SignIn**, even if the connected logs do not yet contain completed requests for either. SignUp is detected automatically from the EntryFlow WatchDog format `Metadata SignUp Staged. Now asking for Logic Discovery...` (or `Logic Node SignUp discovered at ...`). Classification is limited to lines belonging to the current completed lifecycle so that a previous SignIn request cannot cause a SignUp to be mislabeled. Other detected and custom operations follow alphabetically. Incomplete requests are not used for timing measurements.
